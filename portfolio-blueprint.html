01

System Architecture - Why Three Languages

The system has three layers. Each was built in a different language - not to show off, but because each layer has fundamentally different requirements that made different tools correct.

Python
Discord Gateway
Handles the Discord event stream. asyncio fits naturally with Discord's WebSocket gateway - thousands of concurrent events, all I/O bound. Best library ecosystem for Discord's API lives in Python.
Async I/O
Event-driven
Best Discord libs
Rust
Data Access Layer
Handles all database operations and real-money transactions via Axum. GC pauses are unacceptable in a payment path. Rust's ownership model guarantees memory safety without a runtime. libSQL embedded in-process eliminates network latency entirely.
No GC pauses
Memory safety
Financial path
Next.js
Web Dashboard
Server-side rendered admin dashboard for monitoring server economy, user stats, and event management. Deployed on Cloudflare Workers for edge performance.
SSR for dashboard
Edge deployment
React ecosystem

02

The Database Evolution - Driven by Real Failures

This is the most honest part of the case study. Every database migration happened because something broke, something scaled poorly, or something cost too much latency. Here's the progression.

🔴 Problem: Concurrent Writes Crash
Raw JSON File → MongoDB Sharded Cluster
JSON files can't handle concurrent writes. Multiple economy transactions crashing the bot was the forcing function to learn proper databases. Chose MongoDB's sharded cluster specifically for write throughput.
🔴 Problem: Query Latency
Added Redis Caching Layer
As member count grew, read latency became noticeable in user-facing interactions. Redis caching for hot data (active user economy states) brought response times down significantly.
🔴 Problem: Relational Data Needs
MongoDB → PostgreSQL as Primary
The economy system developed complex relational requirements - transactions, balances, event histories - that document stores aren't built for. Migrated to PostgreSQL while keeping Redis as the caching layer.
🟢 Optimization: Network Overhead
libSQL Embedded in Rust Process
Built the Rust Data Access Layer with gRPC for Python communication. Then took it further: embedded libSQL directly inside the Rust process to eliminate network round-trips for the most latency-sensitive operations entirely.
🟠 Curiosity: Can We Do Better?
Partial Custom Redis Implementation
Wasn't satisfied with off-the-shelf Redis behavior for specific caching patterns. Built parts of a custom Redis implementation to achieve better results for the specific access patterns of the economy system.
🎨 Design Intent - Database Timeline This is the single most impressive section in your entire portfolio for technical readers. The timeline format works because it shows *causality* - each step was forced by a real problem. Color code the trigger labels: red for problems that forced change, green for proactive optimizations, orange for curiosity-driven improvements. This visual alone tells a 5-year engineering story in 2 minutes of reading. The custom Redis detail should be visually distinct - maybe a slightly different card style - because it's the most exceptional data point.

Economy Design - Where Engineering Meets Behavioral Psychology

"A virtual economy with 50,000 participants behaves like a real economy. Inflation, exploitation, reward psychology, and trust - all of it applies."

Inflation Prevention

Controlling money supply through sinks and faucets - events that remove currency must balance events that generate it.

Exploit Detection

Rate limiting, anomaly detection on transaction patterns, and rollback mechanisms for economic exploits.

Reward Psychology

Variable ratio reinforcement schedules in gambling and games. Daily streaks. Loss aversion mechanics. Applied behavioral economics.

Real Money Bridge

Real currency purchase flow via Axum API. Trust, security, and UX around financial transactions in a gaming context.

04

What Went Wrong - The Honest Section

Every senior engineer reading a portfolio looks for this. Anyone can list achievements. Only someone who actually built something can describe what they got wrong.

The Cache Bug Incident. A bug in the Redis cache layer caused three days of user economy data to be lost permanently. Partial recovery from logs was possible but not complete. Response: publicly acknowledged the issue to the 50,000-member community, compensated affected users with virtual currency. Long-term fix: added comprehensive test coverage, log points throughout the transaction path, and auto-recovery mechanisms. Lesson: transparency with users is not optional. Systems fail. Response to failure is what builds trust.

🎨 Design Intent - What Went Wrong The cache bug story is perfect for this section because it shows three things at once: technical failure (the bug), human judgment (how you handled the community), and engineering response (the systematic fix). DAAD evaluators specifically value self-awareness. This section should also include 1-2 architectural decisions you'd reverse - for example, "I'd start with PostgreSQL from day one instead of migrating to it" or "I'd design the gRPC interface differently." Those show current technical maturity, not just past mistakes. The highlight box treatment makes this feel like a retrospective memo, not a confession.

The Person

About

I'm Sudip Roy, known online as drlove. I grew up in West Bengal, India, studying computer science while building things that were probably too ambitious for someone with no experience.

My path into software was unusual. It started with curiosity about how video games worked, led through learning to hack Wi-Fi to play a game (which taught me more about social engineering than any textbook), through Unity and Unreal Engine, and eventually landed on backend systems and distributed architecture.

For the last five years I've been co-owning and building Worldwide - a Discord server of 50,000 people with its own economy, games, and culture. That project has been my real education: not in theory, but in what happens when real people interact with systems you build at scale.

I'm now completing my M.Sc in Computer Science, having previously cleared the GATE exam. I'm looking to bring the practical depth I've built to a world-class research environment - specifically a master's program in Germany where I can be inside a city with the kind of creative tech companies I want to eventually build for or build myself.

Long term: CTO. Maybe founder. Definitely someone who builds things that outlast the building of them.
